# 共享行为语义变更模式库（Semantic-Change Patterns）

> 来源：多轮缺陷修复复盘（含"去掉状态查询条件后已删除记录重新显示""删除提示看不清""导入不支持中文名称"等需求迭代类缺陷）。
> 适用对象：对既有功能的**共享行为**做语义级变更（删除方式、状态过滤、默认值、提示形态、字段解析口径）的修复/迭代任务。

## 触发场景（满足任一即加载本库）

- 新需求/新任务上线后，**旧功能出现异常**（用户报"XX 功能坏了"但该功能代码未被本次改动）
- 修复任务需要**改变既有共享行为语义**：逻辑删除↔物理删除、查询默认过滤值、状态枚举含义、提示组件形态、导入/导出解析口径
- 修复完成后需要**验证闭环但运行环境不可用**

## C1 定性分流：功能缺陷 vs 需求交互缺陷

旧功能异常时先分流定性，避免在旧代码里找不存在的 bug：

| 特征 | 定性 | 处置 |
|------|------|------|
| 异常功能代码近期未被改动，但**其依赖的某个条件被其他任务解除/改变** | 需求交互缺陷 | 根因在"隐含依赖被解除"，修复方向是补齐新需求下的语义（见 C2），不是改旧功能代码 |
| 异常功能自身逻辑错误（空指针/边界/文案） | 功能缺陷 | 按 hook-diagnosis-patterns D1 或常规缺陷流程处置 |

**判断动作**：拿到缺陷后先回答两个问题——①该功能显示正确的前提条件是什么（如"列表默认只显示生效记录"）？②该条件是否被近期需求/任务变更过？任一命中即按需求交互缺陷处置。

## C2 共享行为语义变更影响面矩阵【强制】

改"删除/状态/过滤/解析"类共享行为语义前，必须枚举该行为的**全部读方**逐一定性，任一读方未定性不得动手：

| 读方类别 | 核查点 | 定性动作 |
|---------|--------|---------|
| 页面查询 | 列表/详情是否依赖旧语义过滤数据（如靠默认状态过滤隐藏已删记录） | 语义变更后行为是否仍符合用户预期 |
| 业务校验 | 生效性校验/重复性校验是否按状态枚举匹配 | 确认匹配口径不受影响（如固定匹配生效态） |
| 批量导入/日终任务 | upsert 匹配、定时采集是否读取旧语义下的记录 | 确认其匹配条件与变更后语义兼容 |
| 操作日志/追溯 | 删除前是否已保存快照（删除后无法再查的字段） | 快照先行是物理删除的前置条件 |
| 前端展示 | 翻译/回显是否依赖被变更的字典或状态 | 字典组加载与展示列同步评估 |

**处置规则**：
- 全部读方兼容 → 可实施语义变更，并在变更点注释写明"为什么改"（引用任务号/需求口径）
- 存在不兼容读方 → 先收敛该读方（改其匹配口径或保留兼容层），再变更语义
- 无法穷举读方 → 升级用户裁决，禁止静默选边

## C3 后端契约前置核实【强制】

前端删除查询字段/修改传参结构前，必须先核实后端对该参数的空值分支：
1. 定位后端接收 DTO/Example 组装处，确认参数为空时的行为（跳过过滤 / 报错 / NPE）
2. 后端空值行为 = 前端删字段后的实际效果，二者必须与用户预期一致
3. 禁止只改前端不核实后端——"前端不再传"不等于"后端不过滤"，也不等于"后端不报错"

## C4 框架能力优先【推荐】

需要"码值↔名称互转、字典映射、通用校验"等通用能力时：
1. 先检索框架（served/框架层）是否已有现成服务方法，再决定是否自建
2. 命中现成方法后，**读框架实现核实契约**：返回值是否可能为 null、是否带法人/机构维度隔离、键值方向（key→value 还是 value→key）
3. 禁止凭方法名臆测契约后直接调用

## C5 非法输入拦截前移（fail-fast）

用户可自由录入的解析类输入（导入列/文本框）：
- 值无法解析/翻译时，**在入库前报行级错误**（含定位行号+原始值+可操作建议），禁止"原样入库让下游 miss"
- 理由：非法值入库后表现为"列表翻译 miss/下拉无法回显"等静默异常，排障成本远高于导入时一行报错
- 已合法的旧格式输入必须保持兼容（回归口径）

## C6 修复即注释扩散同步【强制】

实现语义变更（修复/重构）落盘后，对同一语义在**调用链上下游的所有关联注释**执行同步检查：
1. Grep 变更方法名/语义关键词，列出全部命中注释（本类/上游 Service/下游调用方/页面注释）
2. 逐条核对注释描述与实现是否仍一致（如"置失效"vs"物理删除"、"默认查生效"vs"查全部"）
3. 漂移注释当场修复——注释即凭证，失真注释会误导后续修复者恢复旧实现
4. 走查侧对应 bemp-backend-code-review RF-003（checkLogic 含修复性扩散检查点）

## C7 验证等级决策树【强制】

修复完成后的验证路径按环境可用性与改动性质决策：

```
改动是 UI 交互类？
├─ 否（纯后端/配置/常量）→ 编译通过 + 关键分支逻辑走查即可
└─ 是 → 运行环境（前端 dev server + 后端服务）是否在跑？
    ├─ 在跑 → UI 实测通过后 verified:true
    └─ 不在跑 → 判断"启动全套环境成本 vs 改动规模"
        ├─ 小改动（删控件/改文案/改提示时长级）→ 编译+语法级验证
        │   + verified:false + 人工抽查步骤（菜单路径/操作序列/预期结果）
        └─ 大改动（新流程/数据写入/多页面联动）→ 走 startserver 技能启动后实测
```

- verified:false 是诚实标注而非偷懒：回传文档必须给出可执行的抽查步骤
- 环境探测以**项目配置的端口/进程特征**为准，禁止按通用默认端口猜测（会被同端口的其他应用误导）

## C8 执行环境适配（Windows/PowerShell）

| 场景 | 规则 |
|------|------|
| 多行 commit message / heredoc | PowerShell 不支持 `<<'EOF'`，改用多段 `-m` 参数 |
| CLI 传 JSON 等复杂参数 | 转义不可靠（反引号/单引号/`--%` 均有失败面），改为写临时脚本文件后传路径执行 |
| 临时文件路径 | 使用显式绝对路径，禁止依赖 `$env:TEMP` 展开（可能展开为 8.3 短路径导致下游找不到文件） |
| JAVA_HOME 等构建环境变量 | 缺失时从 `_shared/env-config.json` environmentDefaults 解析取值（按配置加载铁律），禁止硬编码本机路径 |
| git 提交 | 每任务独立 commit；先 diff 逐文件三分类防裹挟其他会话 WIP；提交后 `git show --stat HEAD` 核对 |
