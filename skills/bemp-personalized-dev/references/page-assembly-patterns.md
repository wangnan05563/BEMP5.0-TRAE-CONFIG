# 页面组装模式：菜单挂载 / 路由注册 / 独立访问形态

> **触发场景**：①新增/修改页面或弹窗的菜单挂载与路由注册 ②弹窗组件复用为独立菜单页面 ③菜单/路由类缺陷修复的根因定性 ④国际化文案缺失（界面显示 key 原文）。案例溯源：T00870/T00871（2026-09）。
>
> 文中 `{placeholder}` 均为占位符，实际值经银行配置解析链（BANK_CODE → 工程目录/表名/文件 glob）获取，禁止硬编码任何银行真实路径、菜单编码、URL。

## 快速决策树（先走此树，只读命中分支）

```
本次变更是"页面/弹窗的访问形态或挂载方式"？
├─ 否 → 不适用本文档，回 frontend-guide
└─ 是 → F 前置事实核验（第一节，强制）
    ├─ 目标是"已有弹窗组件挂为独立菜单页" → 第二节 standalone 模式
    ├─ 目标是"新增页面/菜单" → frontend-guide 页面模板 + database-guide 菜单 DML
    └─ 目标是"修复菜单/路由/白屏类缺陷" → 第一节定性 + 第二节（若需形态调整）+ 第三节（若文案缺失）
```

## 一、前置事实核验（F1-F4，菜单/路由类变更强制）

菜单状态存在**三个可能互相矛盾的事实源**，任一单一来源定性都是返工根源（案例：仅凭需求文档+增量脚本判定"无独立菜单"→ 删路由 → 实库菜单早已登记 → 动态路由注册空组件 → 白屏依旧）。

| 源 | 核验方法 | 结论形态 |
|:---|:---|:---|
| F1 实库菜单授权表 | 经 bemp-db-operator 回读（产品化表名 TM_AUTHORITY，字段 PATH/AUTH_NAME/AUTH_TYPE/PARENT_AUTH_NO 以实际 schema 为准），条件=目标 PATH 前缀 | 已登记/未登记 + 证据行 |
| F2 deploy 增量脚本 | 对 {dml_script_dirs} 逐条 grep 目标 PATH 关键词 | 命中/未命中 + 文件名 |
| F3 前端路由注册表 | 对银行级路由索引文件（banks/{bankCode}Index 类聚合文件）grep 注册键 | 已注册/未注册 + 行号 |

**F 判断逻辑**：
1. 三源结论各附证据写入缺陷定性记录，**以 F1 实库回读为最高基准**（脚本可未随实盘执行、可存在手工配置）；
2. "需求文档无此菜单"不能推出"实库无此菜单"，反之类推；
3. F1/F2/F3 互相矛盾且无法判定基准 → 暂停修复定性，向需求方/owner 确认菜单预期形态（独立页面 or 弹窗入口）后再继续；
4. 页面访问形态调整（弹窗 ↔ 独立页面）必须同步保持**三元组一致**：菜单登记（F1）+ 路由注册（F3）+ 组件形态（第二节）。

**动态路由白屏链路**（为何删路由会白屏依旧，修复前必读）：菜单驱动路由注册体系下，服务端菜单返回的每个叶子 PATH 都会生成一条动态路由，`component` 取自路由注册表——注册表删了该键 → component=undefined → **空组件路由仍注册成功** → `to.matched.length` 非 0 → 守卫回退逻辑不触发 → 渲染空白。结论：**删注册键消除不了菜单驱动的空路由，只会把"弹窗不可见"变成"页面白屏"**；正确解法是恢复注册 + 组件形态适配（第二节）。

## 二、standalone 独立页面模式（弹窗组件复用为菜单页）

**适用**：组件根节点为弹窗（msgbox/modal）、显隐由父页面传入的 Boolean prop 驱动、依赖父页面传入上下文参数对象——业务方要求将同一组件挂为独立菜单直接访问。
**不适用**：组件无弹窗根节点（普通页面）；上下文强绑定到批次/单据等父页面数据且后端查询接口不支持无上下文查询（此时独立页面无业务意义，应拒绝挂菜单而非改造）。

**前置确认（改造前必查）**：后端列表接口对上下文键（如批次/单据 ID）为空时的行为——为空=查全部（可 standalone）/为空=报错或空结果（不可 standalone，需后端先支持）。

**改造清单（页面化双分支定稿方案）**：
1. **形态判定**（created）：检查 `$vnode.componentOptions.propsData` 是否含父页面驱动 prop（`xxxWin` 类 Boolean 开关）——未传入即独立访问。判定结果存 data（如 `standalone`），全组件据此分支；
2. **模板双分支（定稿方案，禁止外壳退化补丁）**：根节点包一层 `<div>`，浮层组件**整段替换**为页面结构——
   ```html
   <div>
     <!--standalone 页面形态：直接渲染内容区，无任何弹窗外壳/遮罩/浮层 DOM-->
     <div v-if="standalone" class="layout">
       <!-- ⚠ 此区块与下方弹窗形态内容区为同步副本，修改查询条件/表格列时两处必须同步维护 -->
       <div>…查询表单 + h-datagrid…</div>
     </div>
     <!--弹窗形态（原父页面入口）：保持原浮层外壳不变-->
     <h-msg-box v-else v-model="…">…同样内容…</h-msg-box>
     <!--内嵌子弹窗（新增/修改框）上提到根层级，两形态共用一份-->
     <h-msg-box v-model="addOrEditWin">…</h-msg-box>
   </div>
   ```
   要点：①`v-if`/`v-else` 互斥渲染，两分支同名 ref（datagrid/formItem）不冲突；②内嵌子弹窗移出浮层外壳上提至根层级（浮层 transfer 后与位置无关），避免内容三份复制；③页面分支与既有正常页面（`div.layout` + `h-form-search`/`h-datagrid`）**完全同构**——同构是可靠性的论证基础，不依赖任何对库组件的属性/样式 hack；
3. **上下文自备**：父页面传入的字典/参数，standalone 时自加载（created 中按 key 拉字典 → 本地 data 承接；查询上下文键留空走全量，前置确认后端对空上下文键的行为）；
4. **按钮可见性**：依赖父页面上下文才能工作的操作（如"挂到某批次下新增"）在 standalone 分支不渲染该按钮（authObj 对应位置同步置 false 双保险）；仅依赖已有记录 ID 的操作（修改/删除/复核）保留；
5. **事件保护**：向父页面 emit 的关闭/刷新事件仅弹窗分支触发，页面分支天然无关闭动作，无需拦截；
6. **父页面字典完整性**：弹窗形态依赖父页面 dictMap 翻译的列，父页面 mounted 需加载完整字典组（缺组时弹窗列显示原始码值，如复核状态显示 5 而非"已复核"）。

**⚠ 已废弃方案（反面案例，禁止再用）——浮层外壳退化补丁**：曾尝试保留浮层外壳、按 standalone 动态化 `:mask/:closable/:transfer` + width/styles 页面化 + 非 scoped CSS 覆盖运行时类名 + `body:has(...)` 滚动锁兜底。受控环境三场景实测全过，但业务方真实环境复测仍"弹窗覆盖全屏、看不到菜单、切换不了页面、关闭不掉"——**范式级错误无法靠属性/样式补丁修复**：浮层（fixed 定位模型）与页面（文档流模型）是两种渲染范式，退化补丁永远存在环境差异漏洞（窗口尺寸/最大化/库组件内部状态）。遇到浮层根节点组件需要页面化时，**直接走模板双分支，跳过一切外壳保留方案**。

**回归验证（提交前必测，验证口径=与正常页面行为一致）**：
1. 独立菜单/URL 直接访问：菜单/导航可见且**可点击切换**、内容区无遮罩无浮层 DOM（`document.querySelector('[class*=mask]')` 应为空）、表格渲染且分页正常；
2. 切换其他页面再切回：无任何样式残留（body 无滚动锁类、无 mask 残留）；
3. 原弹窗入口（父页面按钮打开）：上下文正确、含完整操作按钮、字典翻译正常（列显示文案而非码值）。

## 三、国际化差异化子段补充与覆盖度校验

**现象**：页面文案显示为 key 原文（英文点号串），主国际化文件正常——页面使用了差异化命名空间（`{ns}.m.{module}.{subModule}.*`）但银行级 zh-CN.js 未定义对应子段。

**流程**：
1. 提取命名空间：grep 目标页面全集（同模块所有 .vue）的 `$t('{ns}.m....')` key 集合；
2. 定位银行语言文件：`views/bizViews/banks/{bankCode}/locale/lang/zh-CN.js`，确认挂载层级与现有子段结构；
3. 新增子段于命名空间对应层级，文案**对照需求文档栏位描述与提示原文**（如"请选中一条数据"类提示按需求原文，不自行措辞）；含占位符的文案确认 `{0}{1}{2}` 个数与调用处 replace 链一致；
4. **覆盖度校验（脚本化，禁止目测）**：页面使用 key 集合（去重排序）与子段定义 key 集合做差集，差集非空 = 漏配；再用 node 实际 require 加载语言文件断言结构可达（`obj.{ns}.m.{module}.{subModule}` 存在且 key 数吻合）；
5. 验证等级：文案类修复静态校验即可（key 集合全覆盖 + 加载断言），无需 UI 实测；若同批还有交互类修复，一并 UI 复测。

## 四、验证等级匹配（与 mtask/交付流程衔接）

| 变更类型 | 最低验证等级 |
|:---|:---|
| 纯文案/国际化 key 补充 | 覆盖度差集断言 + 语言文件加载断言 |
| 路由注册表增删 | 静态 grep + **UI 实测双场景**（第二节回归） |
| 组件形态/standalone 改造 | UI 实测双场景（独立访问 + 弹窗入口） |
| 菜单 DML 落库 | 实库回读 + 登录后菜单可见性实测 |

> GUI 交互类任务**静态验证通过 ≠ 可标已验证**（案例教训：工具默认 verified 掩盖验证等级不足，被人工复验打回）；任务系统回传时未实测只标完成态，验证结论在实测通过后更新。
