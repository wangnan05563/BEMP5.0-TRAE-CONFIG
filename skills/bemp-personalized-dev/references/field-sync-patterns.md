# 字段链路同步模式库（Field-Sync Patterns）

> **触发场景**：①给既有表/实体**新增字段**（扩列/字段扩展），且该字段需在列表/弹窗/导出/日志/快照中展示或落库 ②反馈"某字段落库/展示为空""**修改之后没有记录**""改了但查不到"类缺陷 ③维护 实体↔DTO/VO 等映射（转换）工具。案例溯源：维护日志"规模/成份"四列落库恒为空（上轮只补了映射工具一个方向，2026-10，复盘沉淀 E1-E7）。
>
> 文中 `{placeholder}` 均为占位符（`{目标表名}`、`{日志表名}`、`{实体类}`、`{Dto类}`、`{映射工具}`、`{字段名}`、`{原值列}`、`{新值列}` 等），实际值按目标环境 schema/源码解析，禁止硬编码；"本次实例"栏引用的真实类名/表名/字段仅为本行案例记录，**不构成通用规则，复用时必须替换为目标环境真实值**。
>
> **适用边界**：
> ✅ 给既有表/实体新增字段并需展示或落库；"字段值为空/未记录"类缺陷排查；映射工具（转换器）字段对称性维护；加字段后下游链路漏补的返工修复。
> ❌ 字段**计算逻辑错误**（值算错，非搬运丢失，属常规缺陷）；**有报错堆栈**的缺陷（直接看异常，无需定性分流）；纯前端渲染/布局问题（走 page-assembly-patterns）；钩子/开关**逻辑分支**静默跳过（走 hook-diagnosis-patterns）。

## 快速决策树（先走此树，只读命中分支）

```
现象：某字段"为空 / 未记录 / 改了查不到"？
├─ 有报错堆栈？ → 不适用本文档，直接看异常（未知列/映射错误）
└─ 无报错 → 定性（E1 现象分流）
    ├─ 整行/整条记录不存在 → 写动作链路（E1-a）
    ├─ 记录在、该列空 → 映射工具方向对称性（E3，高发）
    ├─ 前端列缺失/翻译空 → 前端列与字典（E1-d）
    └─ 列都在仍空 → 回 E2 逐环节清单核对
        ↓
加字段类新需求 → 先枚举链路清单（E5）再动手 → 按 E2 逐环节同步
        ↓
无运行环境 → E6 JVM 级断言复现并收口（对照 C7 验证等级决策树）
```

## 一、E1 定性分流：按"现象"定位"环节"

**通用化表述**：接"字段为空/未记录"反馈，第一个动作是按**可观测现象**分流到对应链路环节，据此决定排查入口，禁止直接猜某段代码：

| 现象 | 指向环节 | 排查入口 |
|:---|:---|:---|
| 写入报错（未知列/列不存在） | 表列缺失（DDL 未执行或漏列） | 核对 `{目标表名}`/`{日志表名}` 列定义与 DDL 执行状态 |
| 整行/整条记录不存在 | 写动作未触发或被吞异常 | 写日志/写库的调用链 + 异常处理分支 |
| 记录存在、该列空 | 映射/搬运环节方向不对称（**高发**） | `{映射工具}` 两个方向的 setter 对称性（E3） |
| 前端列缺失，或列在而值与库内不一致 | 前端列配置/字典组缺失或 key 不匹配 | 列 key 与后端属性名一致性 + 字典组加载 |

**本次实例**：反馈"企业规模和经济成份修改之后没有记录"——截图显示弹窗**列已存在但四列全空**（排除前端列缺失）→ 现象归入"记录存在、该列空"→ 收敛到映射工具方向对称性，命中的正是 `{映射工具}` 写入方向漏拷字段。

**判据**：先看"行有无"再判"列有无"——行无 → 写动作问题；行在列空 → 搬运问题。二者排查入口完全不同，混判会白翻一整条链路。

## 二、E2 字段链路完整性矩阵【强制】

**通用化表述**：加字段必须**按数据流向**逐环节同步，任一环节漏补即产生静默丢值或展示缺失。完整环节清单/判据/缺失症状以 [config/field-sync-checklist.json](../config/field-sync-checklist.json) 的 `chain` 为**单一数据源**（配置驱动，禁止在本流程文档里复述硬编码清单）。环节概览：

```
数据库(列定义) → 实体(Entity) → DTO/VO(api+as 双工程)
   → 持久层(Dao.xml: BaseResultMap/Base_Column_List/insert/insertSelective)
   → 转换(实体↔DTO/VO 两个方向)  ← 静默丢值高发点
   → 业务快照(原值列/新值列) → 前端(列配置 + 字典组)
```

**硬规则**（开关与说明见配置的 `hardRules`）：

1. **`converterSymmetry`（双向对称）**：任何 X↔Y 映射工具加字段必须**同时补两个方向**；只补一个方向 → 编译/查询/前端列均正常、唯独值为空（静默丢值）。
2. **`existingChainFirst`（链路先行）**：动手前先枚举该字段需流经的**全部既有链路**（查询/展示/日志/导出/校验/导入），产出链路清单后再改，禁止只改最直观的一处。

**本次实例**：上轮修复按"三处漏补"清单补齐了 表列/DTO/前端列/读取方向，**漏了写入方向**——`{映射工具}` 的 `Dto→entity` 未 `set` 四字段，而 `entity→Dto` 已 `set`；`insert` 为全列写入，四列以 NULL 落库，弹窗全空。修复即补该方向 4 行 setter。

## 三、E3 映射工具双向对称铁律【强制】

**通用化表述**：映射/转换工具（`transXToY` / `convert`）通常是**成对**的（读取方向 + 写入方向）。加字段时对每个方向逐一核对：

1. Grep 目标字段/属性名，列出**全部方向**的搬运方法；
2. 逐方向确认该字段有对应 `get/set` 搬运行；
3. **反向校验**：把字段名在当前文件内 grep，计数应为"方向数"的整数倍（缺一即漏）。

**判据**：字段"在某方向有、另一方向无"是不对称的直接信号；`映射工具` 是本类缺陷最高发的静默点，超过"SQL/DDL 漏列"。

**本次实例**：`{映射工具}` 中 `getOrgEnterpriseScale` 等出现在读取方向（entity→Dto），写入方向（Dto→entity）缺失 → 不对称即根因。

## 四、E4 验证失败反馈优先 + 截图直接取证

**通用化表述**：返工任务（含【验证失败】反馈）的处置顺序：

1. 反馈全文是**修复的第一输入**，优先级高于原描述；逐条引用反馈并说明处置（闭环证据）。
2. 反馈附**截图**时，直接识别截图内容（报错文本/界面列位/空值分布）——截图的"列在而值空"往往直接锁定环节，优于文字推断。
3. 关键列值/归属仍以**数据/代码复核**为准（截图小字易误读，仅作线索——同 hook-diagnosis-patterns D5）。
4. 复现不通过时先判"验证环境是否包含改动"（包时间 vs 修复提交时间），包旧先重打包，不在旧包环境做代码决策。

**本次实例**：反馈仅一句"修改之后没有记录"，歧义较大；拉取截图后确认"弹窗四列存在但全空"，据此定性为搬运丢值而非行缺失，省去整条写动作链路的排查。

## 五、E5 无运行环境时的验证降级：JVM 级断言复现

**通用化表述**：本机无运行环境（依赖服务未启/无数据库/端口被占）而无法端到端实测时，**不要止步于编译**——对"搬运丢值"类缺陷用**最小 JVM 断言**复现并验证：

```
断言模式（配置见 field-sync-checklist.json 的 validation.assertionPattern）：
  构造入参（覆盖有值场景）→ 调用被修复的映射/服务方法 → 断言目标字段被携带
判据：
  修复前断言必失败（证明复现了缺陷）→ 修复后断言必通过（证明修复有效）
  该断言可留作回归护栏
```

- 优先级：`compile + assertion` > 纯静态走查（能证明"搬运"这一环真实生效，而非"看起来对"）
- 仍无端到端证据时**不得标已验证**；交付声明写明"已到达等级 + 缺口 + 补验步骤"，验证等级对照 [semantic-change-patterns.md C7](semantic-change-patterns.md)

**本次实例**：构造 Dto（原值/新值均非空）调用 `{映射工具}`：修复前四字段为 null（FAIL）→ 修复后 01/02/A/B（PASS，exit=0），直接证明缺陷点已修复并留作回归护栏。

## 六、E6 收口口径（诚实标注）

- 端到端/UI 未实测 → **不得标"已验证"**；交付声明给出可执行的补验步骤（操作序列 + 预期结果 + 前置条件，如"DDL 已执行"）。
- 剩余工作（如"部署后 UI 复验"）属**验证缺口**，须落成可跟踪项并如实标注，禁止埋在结论文本里。
- 结论中的"存在性/完整性"断言必须附**真实性证据**（见 SKILL.md 第四阶段 deliveryEvidence），禁止无凭据声明。

**本次实例**：本机无运行环境 → 标注"编译+JVM 断言已达标、UI 冒烟缺口、需重打包部署后复验"，未置 verified，并把复验动作落成独立待办。

## 七、E7 执行环境适配（与 semantic-change-patterns.md C8 互为补充）

| 场景 | 规则 |
|:---|:---|
| 大仓库检索 | 全仓 Grep 极易超时 → **必须先收窄到 `{BANK_CODE}` 个性化工目录**再检索 |
| 构建环境变量缺失 | JAVA_HOME/MAVEN_HOME 等从 `_shared/env-config.json` environmentDefaults 解析，禁止硬编码本机路径（同 C8） |
| Maven 离线 | 内网/无外网时用离线模式（如 `-o`）编译；api 工程改动需先 install 再编 as |
| 多行 commit message | PowerShell 不支持 heredoc → 写入消息文件用 `-F` 传入（同 C8） |
| submodule 提交号 | 跨会话引用提交号前先 `git log` 核实——并行会话 rebase 会改写哈希（同 C8 提交纪律） |

## 八、验证等级

| 变更类型 | 最低验证等级 |
|:---|:---|
| 补映射工具方向 / 搬运字段 | 编译通过 + **JVM 断言**（构造入参→断言字段被携带；修复前必失败） |
| 补 Dao.xml 映射（BaseResultMap/insert 等） | 编译通过 + 产物/SQL 特征核对（列齐补） |
| 补表列 DDL | DDL 脚本核对 + 实库列存在性确认（无库时标注为缺口） |
| 补前端展示列/字典 | 编译（或 script 语法检查）+ 列 key 与后端属性名一致性核对 |
| 端到端展示/落库 | UI 实测（ui-probe）或 API 冒烟落库断言——**未达则不得标已验证** |
