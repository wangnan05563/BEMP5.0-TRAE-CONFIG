# 参考实现深度对齐模式库（Reference-Alignment Patterns）

> 来源：「参考同类型页面/模块设计实现」类开发任务的复盘（典型缺陷：只实现表层可见行为，未实现深层逻辑）。
> 适用对象：存在成熟参考实现、需要向目标侧对齐/移植/适配的功能开发。
> 配置入口：**本库只定义方法论与判断逻辑；层清单、分类枚举、判据、验证等级一律以 [config/reference-alignment-checklist.json](../config/reference-alignment-checklist.json) 为唯一数据源，禁止在此复述或硬编码具体清单项。**

## 触发场景（满足任一即加载本库）

- 需求出现「参照 / 参考 / 对齐 / 同款 / 与 XX 一致 / 保持一致 / 移植 / 适配」等措辞
- 目标侧存在同类型成熟参考实现（同产品→个性化的同类页面与业务链路）
- 功能含**写入侧**（落库/状态流转/金额变动），而非纯展示

## 表层 vs 深层：失败的本质

参考式开发的失败几乎同源——**只对齐了「可见面」**（页面结构、列字段、按钮位置、接口 URL 这些肉眼可验的部分），**把「不可见面」当成了「不存在」**。

| 面 | 构成 | 判定方式 | 是否易被遗漏 |
|----|------|---------|------------|
| 可见面 | 页面结构、列/字段、按钮、弹窗层级、接口路径 | 读页面即可 | 低（默认会做） |
| 不可见面 | 入口权限位、数据契约层级、数据源存在性、**写入侧场景覆盖**、口径函数、粒度语义、差异依据 | 必须读后端/写入点/字典/实库才能发现 | **高（默认会漏）** |

## R1–R7 完整流程（固定步骤）

### R1 触发识别
按配置 `trigger.markers` 命中即加载本库；同时确认**存在成熟参考实现**（否则走常规开发流程，见「不适用场景」）。

### R2 三源事实核验【强制】
按配置 `preconditions.mustVerifyThreeSources` 逐源取证，**三源缺一不可**：
1. **参考实现**：前端页面 **+ 后端接口 + 写入侧**（落库/状态变更）——只读前端即开始仿写是典型失败起点
2. **目标实现现状**：已有页面/接口/表结构/字段能力边界
3. **真实数据**：目标侧表/字段真实存在性与数据分布（空表须升级确认，不得静默选边）

### R3 分层拆解
按配置 `layers`（L1–L7）逐层拆解参考实现。层清单是**配置驱动**的，新增维度只需在配置追加一项，流程无需改动。当前七层覆盖：入口与权限 / 数据契约 / 数据源 / 写入侧与场景矩阵 / 口径函数 / 粒度与语义 / 差异台账。

### R4 差异台账产出【强制闸门】
逐层做「参考行为 → 目标行为 → 差异」比对，落成差异台账（字段见配置 `diffLedger.requiredFields`）。
**闸门**：`diffLedger.gate = pre-coding` —— 台账产出前**禁止进入编码**。这是防止「看到页面就直接仿」的核心卡点。

### R5 差异分类处置
按配置 `diffClassification.categories` 四分类：`portable`（可移植）/ `adapt`（需适配）/ `not-applicable`（不适用）/ `must-new`（需新建），各自按 `action` 处置。无法归类时按 `onUnknown = stop-and-escalate` **暂停并升级用户裁决**，禁止静默选边。

### R6 落地实现
按台账逐项实现，**不得凭直觉精简**。删除任何参考侧依赖（列/接口/辅助链路）前，必须有台账记录与依据。

### R7 逐层回归验证
按配置 `verification.levels` 与各层 `minVerifyLevel` 定级逐层验证。L4（写入侧）与 L6（粒度）必须**造业务数据实测落库结果**，仅编译通过不构成闭环。

## F1–F6 失败模式（对应规避动作）

| 编号 | 失败模式 | 典型症状 | 规避动作 |
|------|---------|---------|---------|
| F1 | 只测可见层 | 忘了入口权限位、忘了详情回查链路 | R2 必须读后端接口与调用链，不只读页面 |
| F2 | 隐式语义未澄清 | 聚合粒度/关联主键 与参考不一致 | R3 的 L6：从**写入点**反推设计约定，界面看不出来 |
| F3 | 写入侧只用「看得见的入口」 | 只改了最直观的 1–2 个写入方法，遗漏生命周期事件 | R3 的 L4：枚举**全部写入点**，并以场景码字典全量取值为覆盖基准 |
| F4 | 口径函数漂移 | 把参考的自定义格式化函数换成通用函数 | R3 的 L5：同语义口径变更必须写依据或还原 |
| F5 | 无罪删除参考依赖 | 目标模型缺某字段就删掉整条辅助链路 | R6：删除前必须有台账记录与替代评估 |
| F6 | 差异无台账 | 差异只存在于脑中，评审无法区分「合理适配」与「漏做」 | R4 强制闸门 + R5 四分类 |

**共同根因**：把「不可见面」当成「不存在」。

## 关键判断逻辑

### 判断一：该不该对齐（适用性判定）
先回答三个问题——① 参考实现是否成熟且无已知缺陷？② 目标侧功能语义是否与参考一致？③ 差异是否需要显式记录？
任一为「否」时按 exclusions 处置（见下）。

### 判断二：对齐「机制」还是对齐「取值」
当参考与目标的**业务规则根本不同**时（如某类交易在参考侧占用额度、目标侧明确不占用），应**对齐机制（何时触发、如何流转）而非对齐取值**，并将该取值差异记为 `not-applicable` 或 `adapt`。

### 判断三：写入侧覆盖完整性
以**场景码字典的全量取值**为基准逐值说明「是否需要写」，而非只覆盖「最直观的入口」。覆盖矩阵存在「未说明」取值即不通过（见配置 `writeSideEnumeration.coverageGate`）。

## 适用场景

- 存在成熟参考实现，目标为「对齐 / 移植 / 适配」（产品化→个性化、A 项目→B 项目、老版本→新版本）
- 需求描述含「参照 / 对齐 / 同款 / 与 X 一致」类措辞
- 功能包含写入侧（落库 / 占用 / 释放 / 状态流转），需要数据完整性保障

## 不适用场景（走常规流程或另定处置）

- **无任何参考实现**的全新功能：本流程无增益，走常规开发流程
- **参考实现本身已知存在缺陷**：直接对齐 = 复制缺陷，应先用缺陷诊断类模式库定性，再决定是否对齐
- **纯样式/文案/序号调整**（无数据链路）：走样式类最低验证即可
- **参考与目标业务规则根本不同**：对齐机制即可，差异须记录为 `not-applicable` / `adapt`，不得强行照搬取值

## 与既有模式库的关系

- 与 `field-sync-patterns`（加字段链路同步）互补：本库管「跨实现对齐的完整性」，后者管「单实现内字段链路完整性」
- 与 `semantic-change-patterns`（共享行为语义变更）互补：本库产出差异台账，语义变更类问题按后者 C2 影响面矩阵处置
- 与 `page-assembly-patterns`（菜单挂载/路由注册）互补：本库 L1 层涉及入口权限与挂载点时联动该库
- 验证等级门槛与 `hook-diagnosis-patterns` D7 / `semantic-change-patterns` C7 同源口径，以本库配置 `verification.levels` 为准
