# 旁路管控实现模式：拦截/校验/限流类个性化需求的落点选择与判定口径

> **触发场景**：①需求要求对既有业务链路施加管控（拦截/禁止/不允许/校验/卡控/限流/开关），且约束为**不改产品代码**（以切面/前置判定/拦截器旁路实现）②『管控业务办理成功但应生效未生效』缺陷的排查定性 ③判定某业务状态/方式时系统内存在多套码集（码值同义异构）。
>
> 文中 `{placeholder}` 均为占位符（`{管控入口方法}`、`{目标服务接口}`、`{判定要素字段}`、`{业务唯一键}`、`{同义码值集合}`、`{码值来源}` 等），实际值按目标环境真实代码/库解析，禁止硬编码；"本次实例"栏引用的真实类名/码值/表名仅为本行案例记录，**不构成通用规则，复用时必须替换为目标环境真实值**。
>
> **适用边界**：✅ 个性化旁路管控实现与落点选择、码值同义异构判定、跨环境（内网/生产）"应生效未生效"反馈分流；❌ 允许直接改产品代码的场景（按增量原则优先）、纯前端渲染/样式/文案缺陷（走 page-assembly-patterns）、有报错堆栈的缺陷（直接按异常定位）、无拦截面纯展示/取数需求、产品与个性化根本不同业务规则的比对（走 reference-alignment-patterns）。
>
> **单一口径来源**：`config/guard-interception-policy.json`（触发词/拦截点矩阵/机制核验/码值同义规则/粒度/失败策略/双重校验/留痕/未生效分流/验证等级），本文档只解释判断逻辑，参数一律回配置取。

## 快速决策树（先走此树，只读命中分支）

```
需求：对既有链路施加管控，且不改产品代码？
├─ 否 → 不适用本文档（按增量开发或直接改产品代码处理）
└─ 是 → G1 需求定性（管控语义 + 落点层级初判）
    ↓
怀疑"某层机制不生效" → G2 机制核验（先做机制否定，再谈换落点）
    ↓
G3 选择拦截落点（服务实现 / 控制器 / 组件 / 框架登记通道）
    ↓
G4 判定口径（码值同义异构 + 等同粒度）★最高发根因
    ↓
G5 失败策略（fail-open / fail-close 论证） + G6 双重校验与留痕
    ↓
上线后反馈"未生效" → G7 分流（发布新鲜度 vs 逻辑缺陷 vs 传递吞并）
    ↓
G8 按变更类型定验证等级（无环境时降级并置 verified=false）
```

## 一、G1 需求定性：先判"管控语义"与"落点层级"

**通用化表述**：接到需求先做两件事——

1. **管控语义识别**：需求是否属于"对既有链路施加管控"（命中 `trigger.markers`：拦截/禁止/不允许/卡控/限流/开关）。若只是新增/展示/取数，不进入本流程。
2. **落点层级初判**：管控发生在哪一层——对外接口入口（接口层）/ 业务服务（服务层）/ 内部组件（组件层）。需求出现"在接口层校验""提交时校验""批次提交前校验"等表述 → 优先接口层；出现"服务内部落库前后""某服务方法执行前" → 优先服务层。层级初判直接决定 G3 的候选集。

**本次实例**：需求原文"在贴现申请模块的批次提交环节增加业务校验"，且约束"校验逻辑应在批次提交接口层同步实现，前后端双重校验" → 定性为接口层管控，落点候选优先控制器与服务实现两个层级。

## 二、G2 机制核验：先做"机制否定"，再谈换落点

**通用化表述**：一旦产生"某层 AOP/切面不生效"的怀疑，**不要直接改落点**，先执行 `mechanismPrecheck` 三步否定：

```
m1 检索框架全局切面切点定义  ─ 确认框架是否已用 Spring AOP 覆盖目标层级
m2 检索产品自带同类切面先例  ─ 确认该层级机制在本工程真实可用
m3 确认目标 Bean 装配与调用路径 ─ 确认调用是否经过代理链路
m1 与 m2 均成立 ⇒ 机制可用，问题不在 AOP → 转向 G4 判定口径 / 数据 / 发布新鲜度
任一不成立      ⇒ 再评估换落点，并写明否定依据
```

判定错误的代价：未做否定就换落点，会引入无必要改动，且**真根因（判定口径）被掩盖**，下一轮仍不生效。

**本次实例**：曾怀疑"服务经远程代理引用导致 Spring AOP 不生效"。读框架层全局切面（切点覆盖全部服务实现与原子实现）＋产品自带同类 `@Aspect` 先例 → m1、m2 均成立 ⇒ 机制可用，否定"AOP 不生效"，把方向拉回判定口径。

## 三、G3 拦截落点选择

**通用化表述**：在"不改产品代码"约束下，按 `interceptionPoints.candidates` 选点，每点须核对 `verify` 与 `risk`，不满足则按 `fallback` 降级：

| 落点 | 适用条件 | 主要风险 |
|:---|:---|:---|
| 服务实现 | 同进程 + 框架已覆盖服务实现层 | 经远程代理调用时不在代理链路 |
| 控制器 | 接口层校验；或服务侧切点无法确认生效 | 入参装配分离（判定要素未同时就绪） |
| 组件/原子 | 管控对象是内部调用而非对外入口 | 覆盖不到对外入口 |
| 框架登记通道 | 产品已有同通道登记先例 | 登记写法随框架版本变化 |

选点纪律（`selectionRule`）：无法确认切点可生效时**必须显式降级到更外层落点**，并在注释与交付声明中记录依据与风险，禁止默认相信切点生效。

**落点判定补充（服务层切面通用）**：服务层切点在被调用时，若判定要素由**另一入参**在方法体内装配，则切面执行时该要素尚未就绪——判定必须取**本次调用已就绪**的参数来源（显式入参优先），不可依赖方法体内部才赋值的字段。

**本次实例**：需求为"接口层校验"，实现选服务实现落点（统一入口，覆盖两个提交分支）。经 m1/m2 否定机制怀疑后保留该落点；判定要素（批次号）取自显式入参对象，而非方法体内才装配的字段。

## 四、G4 判定口径：码值同义异构与等同粒度 ★最高发根因

### a) 码值同义异构（禁止单值字面量）

**通用化表述**：同一业务语义在系统中常并存**多套码集**（不同规范/不同系统侧、字典与常量并存、前端另有字面量）。判定该语义时若只比较其中一套码值 → **其他同义码值全部落入放行分支**，表现为"条件恒不成立、静默放行"。

“管控为何未生效”排查的定位顺序中，码值口径**排在最前**（先于粒度、先于要素）。

```
判定某业务语义（如某清算方式/某状态）：
1. 先取四处码值来源（产品常量类/字典组/SQL 样本/前端字面量）grep 全部取值
2. 有产品同源口径函数 → 直接复用（口径与产品一致，最稳）
3. 无同源函数 → 穷举同义码值集合，集中为常量，禁止散落字面量
4. 仍不确定 → 以目标环境实测码值为准（远程事实优先于本机推断）
存在未纳入判定的同义码值 ⇒ 不通过
```

**本次实例**：同一"线上清算"语义并存两套码：行内 ECDS 侧一套、人行侧另一套（后者另有同义码）。首版仅判 ECDS 侧码值 → 批次表实际落人行侧码值时**条件恒不成立**，命中原样放行分支，业务始终不被拦截。修复：补入人行侧同义码值并集中为常量（真实码值以目标环境为准）。

### b) 等同判定粒度

**通用化表述**：行号/机构号/ID 用于业务"等同"判定时，须按业务口径选粒度——**跨环节复用字段的编码相等 ≠ 业务等同**。粒度按 `granularityRules.levels`（行号级/机构级/法人级）选择；字段来源可能为其他环节时向更粗粒度收敛，并注释写明"为什么选该粒度"。

**本次实例**：判定"入账行是否属本行体系"不采用行号级相等，而按法人级查机构表（行号+法人号）关联比对，避免分支机构入账场景漏判。

## 五、G5 失败策略：fail-open / fail-close 论证

**通用化表述**：旁路管控自身依赖的查询/服务异常时，放行还是拦截**必须论证**，禁止默认：

```
管控依赖的查询/服务异常 → 下游有兜底保护？
├─ 有 → fail-open（放行主链路，由下游兜底）；异常 error 留痕 + 注释写明兜底点
└─ 无 → fail-close（拦截业务）或中断并给出明确提示；异常 error 留痕
判定要素缺失（关键字段为空）→ 按同口径处理并留痕，禁止静默跳过
```

**本次实例**：管控依赖的机构表查询异常按 fail-open 放行——论证：跨行为正常业务，管控缺失代价小于全量业务被误阻；异常 error 留痕、放行 info 留痕。

## 六、G6 双重校验与留痕

**通用化表述**：

- **分工**：前端"尽力拦截"（仅做同源/相等比较可命中的场景，取不到要素即放行 fail-open，并注释声明**漏拦边界由后端权威兜底**）；后端承担**权威判定**（可查库做粗粒度判定），覆盖前端无法命中的场景。**只做一端即宣称闭环 = 失败模式**。
- **文案一致**：提示文案前后端**逐字一致**，集中为常量引用（禁止两处各写一份字面量）。
- **留痕**：**放行与拦截均须留痕**，含 `logging.requiredFields`（业务唯一键 + 判定要素值 + 判定结论）。留痕是后续"未生效"反馈的直接定位入口。

**本次实例**：前端按登录用户法人号与批次入账行号相等做尽力拦截（注释声明分支机构入账场景漏拦）；后端按机构表做权威判定；两端提示文案逐字一致；放行/拦截均输出含批次号、码值、行号、法人号、操作时间的留痕日志。

## 七、G7 未生效分流（上线后反馈）

**通用化表述**：接到"管控应生效却未生效"反馈**先分流再定性**，禁止直接改代码（分支见 `ineffectiveDiagnosis.branches`）：

| 现象 | 定性 | 动作 |
|:---|:---|:---|
| 日志无任何判定留痕 | 未进运行环境（发布新鲜度）或落点不在调用链 | 先比对打包/部署时间与修复提交时间；再核对落点是否被调用 |
| 有留痕但走放行分支 | 判定口径不成立（码值同义未覆盖/粒度不符/要素空） | 按留痕实际字段值对照 G4 逐项定位 |
| 有留痕且判定命中但未阻断 | 抛出/返回被上层吞并或包装 | 核对上层异常传递链与响应封装 |

配套纪律：**远程事实优先**（目标环境实测码值/数据分布 > 本机推断；本机无法复现不构成排除依据）；需远程逐条核实时按 hook-diagnosis-patterns D4 产出 SQL 判别集。

**本次实例**：内网反馈"管控未拦截"且未附带日志。按 G7 第二分支推演：日志虽未回传，但业务侧已核实判定要素（入账行号与机构表值对应）→ 要素非空，收敛到**码值口径**分支（G4a），最终由业务方实测码值裁决（远程事实）。

## 八、G8 验证等级

| 变更类型 | 最低验证等级 |
|:---|:---|
| 判定口径改（码值同义/粒度） | 编译通过 + 同义码全覆盖核对 + 边界用例断言（编码相等但语义不等） |
| 新增/更换拦截落点 | 编译通过 + 落点可达性确认（日志留痕实测或调用链走查） |
| fail-open/fail-close 论证 | 注释论证 + 下游兜底路径可达确认 |
| UI 交互类 | 目标环境实测；无环境时降级并置 verified=false + 写明人工复验步骤 |
| 远程环境定性 | 判别集逐条回传 + 判读结论落档 |

**环境降级与缺口标注**：本机无可编译工具链/前端生产构建不可用/无法连目标环境时，按 `environmentPrecheck.checks[].failAction` 降级，并在交付声明显式标注验证缺口——**无目标环境实测时禁止标 verified**。

**本次实例**：本机缺 `JAVA_HOME`，定位本机 JDK 后显式设置才完成模块编译；前端生产构建因工具链版本不兼容不可用，降级为 script 块语法校验 + 括号配对；因无法连内网做 UI 实测，`verified` 置否并写明人工复验步骤。
