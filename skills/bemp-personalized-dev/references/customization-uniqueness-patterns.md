# 个性化定制唯一性模式库（CU 系列）

> 单一数据源：`config/customization-uniqueness-policy.json`。本文只讲**为什么**与**怎么判断**，规则参数不在此重复维护。

## 适用场景

- 新增 / 修改 / 重命名 / 合并任何带 `@CustomizedBean`（或项目等价定制注解）的类
- 缺陷现象为「个性化逻辑改了但没生效」「同一条查询时好时坏」「某页面口径与另一页面不一致」，且代码静态看完全正确
- 同一模块出现多个命名风格相近的个性化实现类（并行会话/多轮需求各自新增的征兆）

## 核心机制：为什么会出现「双覆盖」

框架的定制机制是「用个性化实现替换产品化 Bean」，其隐含前提是**一个被定制类只能有一个替换者**。当两个类同时 `extends` 同一个产品化实现并都标注定制注解时：

1. 两个类都能编译通过，启动也不报错；
2. 框架按 Bean 注册/扫描顺序择一注册，另一个成为「孤儿实现」；
3. 孤儿实现中的全部 `@Override` 方法**静默不执行**；
4. 现象只表现为「某段个性化逻辑没生效」，与「代码写错了」在外部表现上完全一致。

因此**不能靠运行现象反推原因**，必须在编码前做结构校验。

## 检测流程（决策树）

```
准备新增/修改个性化类
  └─ 目标父类是谁？（extends 全名）
       └─ 扫全工程：还有谁 extends 同一父类且带定制注解？
            ├─ 0 个 → 正常新增
            └─ ≥1 个 → 冲突，禁止新建第二个
                 ├─ 已有实现是否覆盖了你要改的方法？
                 │    ├─ 是 → 直接在既有实现上修改（推荐）
                 │    └─ 否 → 把新方法追加到既有实现
                 └─ 两个实现各有对方没有的方法 → 走合并协议
```

「直接在既有实现上追加」优于「新建第二个再合并」——后者每次都要付出合并成本，且极易漏方法。

## 合并协议要点

完整顺序见配置 `mergeProtocol.order`，这里强调三个最容易出错的点：

### 1. 方法差异必须三分类，禁止「整类复制覆盖」

先列出两类的 `@Override` 方法签名，分为「仅 A 有 / 仅 B 有 / 双方都有」。双方都有的还要比对实现是否一致：不一致说明两个并行会话对同一方法做了不同改造，属于**业务口径冲突**，必须升级用户裁决，不能静默取其一。

### 2. 字段遮蔽陷阱（最隐蔽）

Java 允许子类声明与父类 `protected/public` 同名字段，这构成**字段遮蔽**：父类方法读父类字段，子类方法读子类字段。合并时若因为「父类已有同名字段」而省略迁移：

- 迁移过来的方法会改读父类字段；
- 父类字段的注入注解/时机可能与原类不同（例如远程引用 vs 本地注入）；
- 运行期表现为空指针或取到未初始化值，而编译完全通过。

**处置**：迁移方法依赖的字段，连同声明与注入注解一并迁移；在类注释写明遮蔽事实与「二者指向同一服务」的等价性论证，防止后续维护者误删。

### 3. 迁移不等于重构

合并是**搬迁**，不是优化时机。判定条件、默认值、错误文案、排序子句、分页参数必须逐字保持。任何「顺手改好一点」都会让合并后的行为无法与合并前对照，回归验证失去基准。

## 失败模式清单

| 编号 | 现象 | 根因 | 定位方式 |
|---|---|---|---|
| F1 | 个性化改动「没生效」，代码正确 | 双覆盖，落选类的方法不执行 | 按父类分组统计实现数 |
| F2 | 合并后报空指针/字段为空 | 字段遮蔽，未迁移子类字段 | 比对子类与父类同名字段的注入注解 |
| F3 | 合并后某方法行为变了 | 双方同名方法实现不同被静默取其一 | 方法三分类时逐方法比对实现 |
| F4 | 同父类出现两个仅大小写/前缀不同的类 | 并行会话各自新增 | 近似命名检测 + 人工裁决 |
| F5 | 删除旧类后编译失败 | 遗漏 import/实例化引用 | 删除后全工程 Grep 类名，代码引用须为 0 |

## 验证等级

合并属于**结构性变更**，编译通过只证明语法正确，**不能**证明定制加载生效。必须区分：

1. 编译级 —— 语法与依赖正确；
2. 静态级 —— 唯一性分组 count=1、残留引用=0、字段遮蔽逐项核对；
3. 运行时级 —— 服务启动后确认目标 Bean 为个性化实现且口径生效。

无运行环境时按静态级交付，并在交付声明中写明「定制加载未实测」。

## 反模式

- ❌ 「我先新建一个类，回头再合并」——回头往往不会来，冲突被带入提交
- ❌ 「两个类都留着，框架会选对的那个」——选择依据是注册顺序，不是业务正确性
- ❌ 「合并时顺便把命名/结构优化一下」——失去与合并前的对照基准
- ❌ 删除类后只看编译通过，不 Grep 残留引用
- ❌ 用「运行现象正常」证明唯一性——孤儿实现不执行时现象可能恰好符合预期，掩盖问题
