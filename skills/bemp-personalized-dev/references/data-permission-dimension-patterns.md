# 数据权限维度与管控生效模式库（DP 系列）

> 单一数据源：`config/data-permission-policy.json`（维度矩阵 / 入口枚举 / 失败策略 / 开关注册表）。本文只讲**为什么**与**怎么判断**。

## 适用场景

- 需求涉及「谁能看到 / 谁能操作」的数据可见性、归属判定、权限校验
- 现象为「某机构能看到不该看的」「合法请求被拦住」「某入口有校验、另一入口没有」
- 过滤/查询条件改动，尤其是「按机构 / 按法人 / 按客户收窄或放开」

---

## 一、维度错配：用错了「主体」的字段

### 问题本质

业务上「归属」是有层级的：法人 ⊃ 机构 ⊃ 客户 ⊃ 账号。**每个层级有自己的归属字段**，而系统里这些字段常常长得很像（都叫「机构」），于是很容易跨层取用：

| 主体维度 | 典型承载字段 | 误用后果 |
|---|---|---|
| 法人 | 各实体的法人号 | 口径过宽，跨机构可见 |
| 机构 | 创建机构 / 归属机构 / 开户机构 / 操作机构 / 申请机构 | 同概念多字段，口径分叉 |
| 客户 | 客户号、客户的机构字段 | 多账号客户的误拦/越权 |
| 账号 | 账号开户机构、账号号 | 按客户级字段判定则粒度错 |

### 判断方法

1. **先声明主体维度**：这次判定的是「谁的操作是否允许」还是「谁的数据是否可见」？主体是机构还是账号还是客户？
2. **再看字段承载实体**：所选字段属于哪个实体？实体维度必须与主体维度一致。客户实体上的机构字段属于**客户维度**，不能用于账号级判定。
3. **多账号/多实体时的组合语义必须明确**：是「任一满足即放行」还是「全部满足才放行」？必须与业务口径一致并写入注释——这条不定清楚，实现就靠猜。

### 典型误配

> 用「客户」的开户/创建机构判定「客户名下账号」的开户机构权限。
>
> 为什么错：多银行开户客户的「客户级机构」可能是集团级或非简单机构，而其在本行的账号开户机构是本机构。按客户级判定 → 合法请求被误拦；反过来的场景（客户级机构满足但账号不满足）→ 越权放行。
>
> 正确：按账号逐条取开户机构，明确多账号时的放行组合语义。

## 二、语义同源：同一概念，不同入口不同字段

「提交机构」这类业务概念，在不同表里有不同字段：

- 单据表可能记 **申请机构** 与 **操作机构**；
- 客户表记 **创建机构**（≈客户归属）；
- 账号表记 **开户机构**；
- 审计表记 **申请机构**。

若不同页面各自选了一个「看起来像」的字段，就会出现：**页面 A 按申请机构收窄、页面 B 按创建机构收窄**，同一批数据在不同页面可见性不同，且每处代码单看都「合理」。

### 处置原则

1. 同一业务概念在**全部入口**映射到**同一语义字段**；
2. 数据源确实缺该字段时，允许近似映射，但必须**登记偏差说明**（写注释 + 交付声明），且近似字段不得被当作精确语义使用；
3. 变更口径时，同步更新所有入口与相关注释（注释漂移本身也是缺陷）。

## 三、管控生效：代码写了不等于生效

这是「校验/过滤」类缺陷最高发的一类，三种子形态：

### 子形态 1：入口覆盖不全

只改了界面主入口，遗漏邻近入口（修改 / 删除 / 注销 / 撤销等）。用户换个按钮就能绕过，管控形同虚设。

**处置**：以业务动作为线索枚举全部写入/查询入口，产出入口清单（入口 → 触发路径 → 是否经过管控点）写入交付声明。**特别检查内部复用方**——同一服务方法常被定时任务、渠道自动流程复用，改错会误伤或漏控。

### 子形态 2：入参形态不一致导致静默放行

管控判定依赖某字段（如客户号），但部分入口前端**只提交关联 ID**（如账户签约 ID），判定取不到值 → 走「取不到就放行」分支 → 该入口等效无校验，且**无日志、无迹可查**。

**处置优先级**：反查补齐 > fail-close > fail-open（fail-open 必须论证下游兜底并 error 留痕）。

关键认知：**「无法判定」必须是显式分支**（有日志、有结论），不能与「正常放行」共用一条路径——否则事后只能靠排除法排查。

### 子形态 3：依赖产品化参数开关，开关取值把过滤放开

过滤逻辑写在个性化代码里，但底层产品化实现是否真的按机构过滤，取决于一个**业务参数开关**。若实例配置为「放开」态，代码侧精心构造的过滤条件会被架空，现象是「父级能看到下级数据」，而排查方向会被误导到代码侧。

**处置**：开发前按开关注册表确认取值与语义；放开态必须在交付声明与评审报告中**显式告警**并提交业务方决策；**个性化侧优先构造不依赖该开关的强制收窄**（直属 DAO/Example 条件），而不是依赖产品化开关。

## 四、固化加固项：条件片段的语义方向

复用既有条件片段（Criteria 片段 / SQL 片段 / 工具方法）时，最容易犯的错误是方向反了：

- 原片段语义是「**排除**某类记录」，被用成「**仅保留**某类记录」；
- 标志字段按直觉假设「正常态 = 1」，实际业务写 0 → 条件恒不成立；

后果分别是「查询恒为空」和「过滤恒不生效」，且编译完全正常。

**处置**：复用前回读原实现的使用场景确认方向；枚举/标志字段必须核对实际数据取值；**新增过滤条件后必须用真实数据验证结果集非空且符合预期**，禁止以编译通过结案。

---

## 五、验证等级

数据权限类改动直接影响可见性边界，证据要求最高：

| 等级 | 证明什么 | 可否标 verified |
|---|---|---|
| 编译级 | 语法正确 | ❌ |
| 静态级 | 字段归属、入口清单、开关取值经源码与配置交叉核对正确 | ❌ |
| 运行时级 | 越权账号看不到、有权账号能看到 + 日志命中判定分支 | ✅ |

无运行环境时按静态级交付，并在交付声明显式标注「可见性未实测」；**涉及权限边界时禁止以编译通过结案**。

## 反模式

- ❌ 只看代码里「有没有过滤条件」，不证明它在运行期生效
- ❌ 把「取不到判定依据」当作「无需管控」直接放行
- ❌ 依赖产品化参数开关实现收窄，不确认开关实际取值
- ❌ 改动可见性后只编译，不造数据实测
- ❌ 复用既有条件片段时只看语法，不核对语义方向与字段真实取值
