# 断言锚点背书自检（Assertion Anchoring）

> 来源：反洗钱四阶段校验需求用例评审暴露的断言类缺陷（2 严重 2 主要中的断言失真项）。
> 核心规则：**一切断言（预期文案/顺序/行为/参数）必须引用运行时探测到的代码锚点，禁止凭需求文档描述或记忆编写。**

## 锚点定义

可背书断言的代码锚点包括：

| 锚点类型 | 形态 | 适用断言 |
|:---|:---|:---|
| 文件:行号 | 源码中方法/文案/参数的真实位置 | 文案断言、顺序断言 |
| DAO 列清单 | mapper XML 的 Base_Column_List / resultMap | 字段名断言、数据落库断言 |
| 单测实测拼接形态 | 运行单测捕获的实际输出/拼接结果 | 文案拼接断言、组装顺序断言 |

无锚点背书的断言在用例评审中按「预期结果无依据」处理。

## 三类典型翻车案例

### 案例 1：组装顺序断言与代码相反

凭需求文档的叙述顺序编写"先 A 后 B"断言，未核对代码实际执行顺序。运行时校验逻辑可能先执行 B 的校验分支再执行 A，导致断言方向整体反转，正向与反向用例双双误判。
**背书方式**：grep 定位校验方法的分支真实排列顺序，以代码顺序为断言顺序。

### 案例 2：文案断言未含模板拼接后缀

错误提示文案在代码中是"模板前缀 + 动态后缀"拼接生成，断言只写了裸前缀。单测实测的完整拼接形态含后缀（如业务键/字段名回填），裸前缀断言过弱无法拦截真实缺陷。
**背书方式**：跑单测或读拼接代码，断言完整拼接形态（含后缀结构）。

### 案例 3：参数字段名凭记忆

断言中的参数字段名（如请求 DTO 属性名、DAO 列名）凭印象书写，与实际字段名存在大小写/单复数/命名风格偏差，导致执行时字段取值恒为空，断言形同虚设。
**背书方式**：读 mapper XML 的 Base_Column_List 或 DTO 定义，逐字段核对后写入断言。

## 锚定操作清单

编写断言前，按以下顺序完成锚定（每步产出即锚点）：

1. **grep 方法真实顺序**：定位目标校验/组装方法，确认分支与调用的真实排列顺序 → 顺序类断言以此为准
2. **跑单测看实际拼接**：执行相关单测或最小复现代码，捕获实际输出形态 → 文案类断言以此为准
3. **读 mapper 确认表列**：读取目标表对应 mapper XML 的 Base_Column_List / resultMap → 字段名与列清单类断言以此为准
4. **回填锚点引用**：在用例的预期结果或验证点中标注锚点出处（文件:行号 / mapper 文件 / 单测名）

## 自检时机与失败处理

- **时机**：每条含明确预期文案/顺序/字段名的用例编写完成后立即执行；数据准备 SQL 落库前配合 `config/test-data-check.json` → `checkItems.data-sql-schema-verify` 执行
- **On Failure（找不到锚点）**：断言降级为"行为级"描述（如"校验不通过"）并标注 `锚点缺失`，不得虚构具体文案/字段名；在用例评审中声明待锚定
- **On Failure（锚点与用例冲突）**：以锚点为准修正断言；若需求文档与代码冲突，按缺陷上报流程确认需求意图
