# 复用优先测试策略操作指南（P10）

> 模式来源：`_shared/test-workflow-retrospective.md` P10（失败点 W10-01）。
> 核心铁律：测试资产承接一律以实盘为准，上游口述统计数字仅作线索，禁止凭口述数字直接重编全套或排期。

## 一、基数实盘核实规则

上游传递的用例基数（条数/覆盖范围）在承接时**必须实盘核实**，未核实前不得作为排期、映射、评审范围的依据：

1. **实盘动作**：Glob 用例目录（模式占位符化，如 `{case_dir}/*.{case_ext}`）+ 读取用例索引/文件本体，统计真实基数与编号分布。
2. **实盘优先级**：索引文件计数 → 文件系统实际文件数，两者不一致时以文件系统为准并向索引维护方反馈。
3. **无法实盘时**：显式声明"数字仅为线索"待核实，写进承接文档头部；禁止默默采信口述数字。
4. **偏差反馈**：实盘与口述不一致 → 以实盘为准，并将偏差明细（口述值 vs 实盘值 vs 差异项）反馈给上游，留档可追溯。

## 二、四步流程

### 步骤1：资产盘点

- Glob 扫描用例目录与索引文件，产出资产清单：用例编号段、文件分布、覆盖的功能域。
- 记录实盘基数（文件数、用例条数、编号最大值/空洞段），作为后续映射与增量编号的基准。
- 盘点结果落盘为资产清单文档（路径占位符化，禁止硬编码具体部署路径）。

### 步骤2：覆盖度映射表（模板）

| 功能点（新需求） | 既有用例编号 | 处置 | 说明 |
|----------------|-------------|------|------|
| {feature_point_1} | {existing_case_id} | 复用 | 预期结果与需求一致，直接纳入回归 |
| {feature_point_2} | {existing_case_id} | 修订 | 预期结果/前置数据需按新需求调整，注明修订点 |
| {feature_point_3} | —（无对应） | 新增 | 分配新编号，走完整用例设计流程 |

- 逐功能点标注处置：**复用 / 修订 / 新增**，禁止出现既不映射也不标新增的"悬空功能点"。
- 映射表本身是评审对象：映射错位（功能点挂错用例）比缺用例更具迷惑性。

### 步骤3：增量修订规则

- **保持既有编号格式，不重编**：既有用例编号一律保留原值（编号承载历史执行记录与缺陷关联，重编会切断追溯链）；新增用例按既有格式追加新编号。
- 修订仅改必要字段（预期结果/前置数据/步骤描述），修订处在用例文档中留痕（修订说明 + 日期）。
- 复用项不改内容，仅在映射表登记；若复用项执行中发现失效，升级为修订项并留痕。

### 步骤4：增量评审范围

- **复用项**：抽检（核对映射正确性，不逐条全审）。
- **修订项、新增项**：全审（逐条过评审门禁）。
- 评审材料 = 映射表 + 修订/新增用例，不含未变动的复用项正文——评审范围收敛，避免把存量资产反复送审。

## 三、适用与不适用场景

### 适用场景

- 需求迭代（在已测功能域上叠加增量需求）
- 回归测试（存量用例为主、新增用例为辅）
- PRD 小版本升级（功能点与既有用例存在明确对应关系）

### 不适用场景

- 全新模块（无既有资产可盘点，直接走完整用例设计流程）
- 资产结构差异大（既有用例组织方式/粒度与本次需求无法建立可维护的映射关系，强行映射的维护成本高于重编）

## 四、反模式示例

**反模式：凭口述数字直接重编全套**

- 上游口头说"大概有 N 条用例，你直接重新编一套就行"，承接方未实盘核实便按口述 N 条排期并重编全套用例。
- 后果链：①排期基于失真基数，实盘后工作量评估失效；②重编切断了既有编号与历史缺陷/执行记录的关联；③评审范围被迫扩大到全套（本可只评审增量）；④上游口述与实盘的偏差无人留痕，同类偏差下次继续发生。
- 正确做法：先按"一、基数实盘核实规则"实盘 → 出映射表 → 增量修订 → 仅评审增量。
