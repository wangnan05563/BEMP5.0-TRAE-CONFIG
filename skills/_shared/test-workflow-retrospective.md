## 一、已知失败点及规避策略

| 序号 | 失败点 | 根因 | 规避策略 |
|------|--------|------|---------|
| 1 | URL前缀缺失 | 前端 API 路径缺少个性化前缀 | 前端代码评审增加 URL 前缀检查规则 |
| 2 | 后端方法未重写 | 个性化 Controller 未重写产品化方法 | 后端代码评审增加方法覆盖检查 |
| 3 | 截图路径阻塞 | MCP workspace roots 未配置 | 配置 MCP workspace roots 或使用默认路径 |
| 4 | Oracle MCP 只读 | MCP 仅支持 SELECT | 使用 MySQL MCP 或 Java JDBC 执行 DML |
| 5 | Playwright channel 限制 | MCP 不支持 channel='chrome' | 使用 Chrome DevTools MCP 替代 |
| 6 | 任务描述路径错误 | 产品化 vs 个性化文件混淆 | 任务描述明确标注个性化文件路径 |
| 7 | PowerShell 变量丢失 | 嵌套调用 $r 被吃掉 | 避免嵌套调用，使用脚本文件 |
| 8 | Oracle 版本不兼容 | 11.2 不兼容 12c+ | 使用 ojdbc8 驱动 |
| 9 | class 加载优先级 | jar 中 class 优先级低于 classes | 复制 class 到 WEB-INF/classes |
| 10 | fill 工具截断 | 长字符串被截断 | 改用 evaluate_script + Vue $set |
| W8-01 | 弹窗内嵌 Datagrid 首帧空数据 | gridData watcher 无 immediate + autoLoad 空分支 setGridData 被注释，弹窗复用旧实例 | 弹窗内 `v-if` 重建实例 + `:autoLoad="false"`；评审规则已沉淀至 bemp-frontend-code-review check-dialog-component.js（J-HD1） |
| W8-02 | scoped 样式对子组件 render 元素失效 | scoped 属性选择器只命中本组件模板节点 | 移入独立非 scoped 块 + 唯一类名前缀隔离；评审规则 J-SC1 同上 |
| W8-03 | PowerShell 双引号吞占位符 | PS 插值 `${ENV:...}` 产生假失败 | 冒烟命令外层用单引号或写临时脚本文件执行 |
| W8-04 | ZK 端口三处配置错配（2181 vs 21811） | startserver 端口知识未同步测试技能 | 全链统一 `${ENV:BEMP_ZK_PORT:21811}`（W6-02 同源） |
| W9-01 | 源码已编译但 deploy jar 为旧包，服务启动加载不到新类 | 增量开发只编译业务模块未重装 deploy 模块，旧包问题在启动/健康检查阶段才暴露且难定位 | 启动前执行产物新鲜度检查（FOUND-IN-JAR/时间戳对比），检出旧包即按 `mvn install -pl {变更模块},{deploy模块} -am` 刷新；已配置化：bemp-automation-startserver config/pre-compile-check.json checks.deployArtifactFreshness |
| W9-02 | 配置文件引用的 sonar Token 401 失效，误判为服务不可用 | Token 失效≠服务不可用；MCP server 进程环境块注入的有效 Token 未纳入解析链 | Token 解析链新增 mcp_process_env 来源（失效后继续取下一来源而非直接终止），敏感 Token 仅入内存不落盘；已配置化：bemp-sonarqube-mcp config/scan_config.json token_resolution_order |
| W9-03 | 回扫"新增问题"虚高（基线漏报被计为新增） | 首次补齐 sonar.java.test.binaries 后类型解析完整，基线漏报规则问题浮现 | CLI 扫描强制携带 java.binaries/test.binaries（sonar-java 硬要求）；对比核销报告单列"口径差异暴露"类目；已配置化：scan_config.json cli_fallback.java_binaries + degradation-chain.md L2 核销口径 |
| W9-04 | 数据就绪 SQL 的 JOIN/WHERE 使用目标表不存在的列（B.BILL_ID），执行必报 ORA-00904 | 凭列名语义相似推测：把 A 表外键列当 B 表主键关联，未对照 mapper 主键查询口径 | SQL 落盘前逐列对照 mapper Base_Column_List/主键查询方法（selectById where ID = #{id}），不确定列先 DESC 实测留档；已配置化：bemp-testcase-generator config/test-data-check.json checkItems.sql-column-existence-check（critical） |
| W9-05 | 评审回退修复后复审，发现修复清单中有项遗漏未改 | 修复方未逐项自验清单，直接整批提交 | 修复方提交前必须逐项勾验修复清单并附每项落点证据；复审走快速通道仅核对修复项（免全量重审）；见 P7 |
| W9-06 | 同一文件多处编辑并行执行，部分修改被覆盖丢失（本会话 5 处） | 并行 Edit 同文件存在写入竞态（W8 期已验证过一次，非偶发） | 同文件多处编辑必须串行执行并在收尾全量验证落盘状态；跨文件才可并行；见 P9 |

## 二、W8 全流程成功路径（最短可复现）

```
PreCheck + start-bemp-env.ps1 启动 5 服务（全UP）
  → 测试用例承接（bemp-test-common 统一索引）
  → 五段式回归（登录→导航[menu_path配置+叶子dump兜底]→注入→断言[响应/样式/console三通道]→清理落盘）
  → 缺陷双重定位（共享组件源码 ↔ 浏览器组件实例转储互相印证）
  → 最小侵入修复（不动共享框架组件，修复收敛在个性化文件）
  → 回归验证 → 报告落盘（round6_bugfix_regression_report.md + 截图）
```

## 三、适用场景与不适用场景

### 适用场景
- BEMP 票据系统银行个性化开发测试
- 需求驱动的功能测试（有明确PRD）
- Web 端到端测试（前端+后端+数据库）
- 多阶段流程化测试
- Vue2 + H-UI 弹窗/Datagrid/提交阻断类缺陷回归（W8 增补，详见 bemp-chrome-devtools-test/references/regression-patterns.md）

### 不适用场景
- 纯后端 API 测试 → 需 api-test-pro
- 性能测试 → 需 bemp-jmeter-test
- 安全测试 → 需专门安全工具
- 移动端测试 → 需移动端框架
- 非 BEMP 项目 → 流程映射不适用
- Vue3 组件实例遍历（$children 失效，需 findComponent/provide-inject）

## 四、工作流级模式

### P5 并行合并终验

- **规则**：≥2 个智能体并行修改同一模块后，必须由独立第三方（未参与该轮并行修改的智能体）以全量编译 + 全量测试执行合并终验；禁止采信各并行方自报的局部结果作为合并结论。
- **适用**：多智能体并行开发/修复存在文件交叉或共享依赖的场景（同一工程、同一配置层、同一前端入口映射）。
- **不适用**：严格按文件边界切分、互不触碰的并行任务（合并后执行一次轻量编译确认即可，无需全量测试）。
- **来源**：反洗钱四阶段校验需求中并行修改后未做统一终验，导致合并态问题被各方自报结果掩盖。

### P6 外部依赖标注协议

- **规则**：BLOCKED/⏸ 标注必须写明回归条件（何种数据/环境/配置/服务就绪后可执行），并随交付文档移交跟踪；禁止只写"BLOCKED"不写条件的空标注。
- **适用**：受外部数据、环境、服务、第三方配置制约的用例与交接事项（如等待特定测试数据、等待外部系统开通）。
- **不适用**：全自主可完成的任务（内部失败应走缺陷闭环与回退规则，而非外部依赖标注）。
- **来源**：反洗钱四阶段校验需求中部分用例因外部数据未就绪被标 BLOCKED，但回归条件缺失，交付后无法判断何时可恢复执行。

### P7 评审回退快速通道复审协议

- **规则**：评审回退修复后，复审按两步走——①修复方提交前必须逐项勾验修复清单，每项附落点证据（文件:行号 或检索结果），禁止整批口头声明"已修复"；②复审方走快速通道仅核对修复项（免全量重审），核对时以代码/文档事实为锚逐项验证，不采信自报。
- **适用**：评审问题修复面小于全量 30%、且修复不引入设计变更的场景（文案更正/SQL 修正/引用错位/统计口径等）。
- **不适用**：修复引发设计变更、新增用例占比过高、或首轮评审未完成的场景（须全量重审）。
- **来源**：六阶段签收校验用例评审回退修复后，快速通道复审抓出修复清单中 1 项遗漏（W9-05），验证了"逐项勾验 + 定向复审"闭环的必要性。

### P8 子智能体写入通道故障降级协议

- **规则**：子智能体遭遇 IDE 写入通道故障（Write/Edit/RunCommand/Glob/LS 超时或序列化异常）时：①先做通道级排查（替代写入通道 + 参数序列化变体），禁止立即放弃；②确认不可恢复后按降级处理——全部产出内容在最终回复中完整定稿（含逐文件落盘指引：目标文件/追加位置/追加方式/收尾复核检索式），标"⚠ 降级"，禁止虚构落盘成功；③通道恢复后由新子智能体按指引补落盘并检索复核，复核通过前该阶段不得视为完成。
- **适用**：子智能体执行期 IDE 桥接层故障；产出物可文本定稿的场景（用例文档/报告/配置条目）。
- **不适用**：产出依赖执行过程实时状态（如必须现场运行命令取回数据）且通道不可恢复时——应标 BLOCKED 写明回归条件（P6）后终止，禁止凭记忆补造数据。
- **来源**：六阶段签收校验测试用例编制阶段写入通道全故障，内容回复内定稿后由后续子智能体按指引补落盘成功（5 文件检索复核全通过）。

### P9 同文件多处编辑串行铁律

- **规则**：对同一文件的多处修改必须串行执行（一次一处、落盘确认后再下一处），并在收尾以全量检索验证所有修改点的最终落盘状态；跨文件编辑才可并行。并行 Edit 同一文件存在写入竞态，后写覆盖先写导致部分修改静默丢失。
- **适用**：任何技能/智能体对同一文件的多点修改（文档批量修正、配置多处增补、代码同文件多处编辑）。
- **不适用**：不同文件之间的并行修改（可安全并行）。
- **来源**：W8 期已发生一次；六阶段用例评审修复时再次发生（同文件 5 处首轮修改被覆盖丢失，改串行后逐项补修通过）——两次实证，非偶发，固化为铁律。
