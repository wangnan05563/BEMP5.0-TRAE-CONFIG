# PRD 质量规范

本规范把通用 PRD 撰写规则转成 BEMP 票据系统可执行的检查项，供 Phase 0、Phase 3、Phase 4.5、Phase 5 引用。票据领域规则仍以 `bill-business-rules.md`、`compliance-rules.md`、`ux-rules.md` 为准。

---

## 一、输入分层与标注

| 类别 | 判定 | 处理 |
|------|------|------|
| 确认事实 | 用户原文、附件、规则库或明确来源直接支持 | 可直接写入正文 |
| 产品判断 | 由确认事实推导，用于消除歧义 | 写入时说明推导依据 |
| 假设 | 为继续推进而采用的合理默认 | 标 `[Assumption, TBD]`，进入待确认清单 🟢/🟡 |
| 开放问题 | 缺失且会实质影响权限、资金、合规、核心流程或不可逆操作 | 标 `[TBD]`，进入待确认清单 🔴 |

映射规则：

- 开放问题 → 🔴 阻塞项；项目规则允许测试假设时，按 `config/prd-assumptions-config.json` 生成假设并保留待确认标记。
- 假设 → 🟢 提示项，附默认假设与调整方式。
- 产品判断 → 正文可见，必要时在待确认清单 🟡 说明依据。
- 确认事实 → 正文直接使用，不加标记。

禁止把假设写成事实，禁止用“通常”“一般”“应该”掩盖未确认规则。

---

## 二、产品契约（Phase 0 必填）

提取功能前，先用六个问题锁定契约：

| 要素 | 问题 |
|------|------|
| 主用户 | 谁在什么场景下操作 |
| 核心任务 | 用户要完成的结果 |
| 触发 | 什么事件或操作启动旅程 |
| 完成条件 | 什么可见状态或落库结果证明完成 |
| 共享对象 | 多角色协同时围绕的票据、交易或任务对象 |
| 信任信息 | 后果性操作前必须看到的信息 |

契约不全时，缺口写入待确认清单，不凭猜测补全。

---

## 三、最小完整旅程与 P0

P0 只保留“能进入、能完成、能恢复”的功能：

- 进入条件；
- 完成任务的必要动作；
- 用户可见的完成证据；
- 最重要失败路径的恢复方式；
- 相关 P1 支撑；
- 明确排除的投机功能（仅当不写会造成分歧时）。

每个候选功能追问四件事：解决谁的什么问题、在旅程哪个节点进入、删掉会不会断闭环、依据属于事实/判断/假设。答不全的功能不进入 P0。

---

## 四、功能需求最小深度

每条重要功能必须覆盖四段链，缺失任一段即为深度不足：

| 段 | 必须写清 |
|----|----------|
| 触发 | 谁、在什么前置条件下、通过什么入口发起 |
| 处理规则 | 校验、计算、排序、依赖、分支判断 |
| 结果 | 落库结果、页面反馈、通知对象与时机 |
| 状态变化 | 操作前后状态、允许与禁止的后续操作 |

按需追加字段规则、状态迁移、权限与数据边界、异常（空/阻塞/冲突/超时/取消/重试/权限受限）、后果性动作（确认、授权、证据、撤销、升级）。

---

## 五、共享规则单一定义

以下规则只允许在一个章节定义，其他模块按名称引用，禁止复制改写：

- 角色与权限矩阵；
- 票据或交易对象生命周期与状态迁移；
- 金额、利息、舍入与精度；
- 日期与工作日规则；
- 跨模块校验与数据一致性；
- 通知对象与时机；
- 审计、留痕与保留期；
- 取消、撤回、冲正、重试与升级。

发现两处定义不一致时，先判定唯一版本，再改引用，不得两处并存。

---

## 六、一致性核对（Phase 4.5 强制）

| 维度 | 核对内容 |
|------|----------|
| 术语 | 同一对象或动作全文同名，不与口语混用 |
| 角色 | 角色名称、权限边界、操作人前后一致 |
| 字段 | 字段名、代码、类型、长度、必填、校验规则一致 |
| 状态 | 状态名称、迁移路径、前置条件、终态一致 |
| 金额 | 票面、交易、利息、实付的计算口径与精度一致 |
| 日期 | 出票、到期、贴现、交易时点口径一致 |
| 模块 | 同一规则不在多个模块重复定义或互相矛盾 |
| 范围 | 每个 P0 功能都能指向完成或恢复，排除项有明确说明 |

---

## 七、可追溯与不虚构

- 每条【补充】必须能指向来源：用户原文、规则库编号、示例数据，或标注的假设。
- 未知指标、费率、限额、SLA、监管口径不得编造，标 `[TBD]` 或 `[Assumption, TBD]`。
- 不得把技术实现（框架、表结构、接口路径、存储方案）写成产品需求；接口章节只写契约、字段与交互约束。
- 不得用“提升体验”“优化流程”等不可验证表述替代具体行为。

---

## 八、文档深度

| 场景 | 深度 | 处理 |
|------|------|------|
| 小改动或单点规则补充 | Light | 背景 + 变更行为 + 受影响共享规则 |
| 新功能模块 | Medium | 契约 + 范围 + 完整功能模块 + 共享规则 |
| 新业务流程或多角色协同 | Heavy | 契约 + 角色与对象模型 + 完整状态机 + 依赖 |
| 涉及资金、权限、删除、审批、合规 | Risk-adjusted | 无论大小都补确认、授权、证据、撤销、升级 |

篇幅不是质量目标。小需求可以几节写完，复杂流程可以很长；不得为凑结构增加空章节。

---

## 九、写作规则

- 写产品在具体条件下做什么，不写“提升体验”。
- 因果逻辑用散文，可枚举项用表格（字段、状态、权限、计算、对比）。
- 同一规则只定义一次，其他位置按名称引用。
- 保留原文一字不改；补充内容集中在【补充】块。
- 模板中某节无内容时删除标题，不留空模板或“待补充”占位。
- 不把内部检查清单、撰写过程、评分表写进交付文档。

---

## 十、交付门禁

| # | 检查项 | 通过条件 |
|---|--------|----------|
| 1 | 产品契约 | 主用户、触发、完成条件、共享对象清晰 |
| 2 | 范围 | 每个 P0 支撑完成或恢复，投机功能已排除 |
| 3 | 可追溯 | 主要补充可指向原文、规则库编号或标注假设 |
| 4 | 需求深度 | 重要功能四段链完整 |
| 5 | 一致性 | 术语、角色、字段、状态、金额、日期无矛盾 |
| 6 | 边界 | 空、阻塞、失败、取消、重试、权限受限已覆盖 |
| 7 | 后果性动作 | 确认、授权、证据、撤销、升级已定义 |
| 8 | 不虚构 | 未知值有标注，技术实现未混入产品需求 |
| 9 | 文档纪律 | 无空章节、重复结论、凑字数 |
| 10 | 交付完整 | 主文档与待确认清单齐全，表格格式合规 |

门禁结果只用于内部修订，不写入交付文档。
