
# BEMP 票据系统 PRD 智能生成器 v1.1

## 定位

**不是帮产品经理写文档，而是帮票据系统的开发、测试、业务分析师补全需求细节，产出一份符合票交所规范、三方都能用的协作基准文档。**

## 核心痛点

| 痛点 | 场景 |
|------|------|
| 需求文档太简略 | 业务只写了功能清单，没写票据状态流转规则、金额校验逻辑 |
| 原型图细节缺失 | 设计稿给了，但票据类型约束、交易金额上下限、日期规则没说明 |
| 合规要求遗漏 | 需求未覆盖票交所报文规范、异常票据库校验、ECDS状态同步 |
| 需求理解不一致 | 口头沟通的需求，开发和测试对票据业务规则理解有偏差 |

## 使用场景

| 场景 | 示例 |
|------|------|
| 会议纪要转 PRD | 需求评审会后，把口头需求转成结构化文档 |
| 原型图识别 | 设计师给了票据操作页面原型，AI 识别字段、按钮、交互逻辑，补全业务规则 |
| 功能清单完善 | 业务只列了功能点，AI 补全票据状态机、金额校验、合规规则 |
| 需求迭代确认 | 初版文档生成后，通过多轮对话逐步完善 |

**目标用户：** 票据系统业务分析师、前端开发工程师、测试工程师

**核心价值：** 把"缺斤少两"的需求来源，补全成一份**信息完整、结构清晰、符合票交所规范、三方认可**的协作基准文档。

## 标准生成流程

### Phase 1: 文档转换

**目标：** 将原始需求文档转为 Markdown 格式，提取结构化内容

**输入格式支持：**
- `.docx` / `.txt` / `.md` — 直接转换
- 直接粘贴的需求文本 — 直接处理
- 图片文件（原型图/截图）— 进入 Phase 2

**执行步骤：**

1. 检测输入类型
2. 若为 `.docx`，按以下优先级转换：
   - 优先：调用 `bemp-advanced-doc-generator` 技能的转换能力
   - 备用A：使用 `bemp-advanced-doc-generator/scripts/convert_docx_v2.py`（需安装 python-docx）
   - 备用B：使用 Trae 内置文档读取能力直接读取 `.docx`
   - 备用C：提示用户手动将 `.docx` 内容复制粘贴为文本
3. 若为 `.txt` / `.md` / 粘贴文本，直接读取内容
4. 提取并保存文档中的图片（如有）
5. **需求分类**：分析需求内容，识别涉及的业务模块（如"承兑"、"贴现"、"额度管理"、"背书"等），用于指导 Phase 4 的审查范围

   **分类输出格式：**
   ```
   需求分类结果：
   - 涉及模块：[承兑, 贴现, 额度管理]
   - 票据类型：[银承, 商承]
   - 交易类型：[出票, 承兑签收, 贴现申请]
   - 涉及页面：[操作表单页, 列表查询页]
   ```

**Phase 1.5 门控检查：**
- `.docx` 输入：统计文档中嵌入图片数量 vs 实际提取的图片文件数量
- `.md` 输入：统计 `![](...)` 引用数量 vs 引用路径的图片文件是否存在
- 粘贴文本 / `.txt`：无图片，跳过 Phase 2
- 若不匹配：**⚠️ 发出警告提示**，列出缺失项，但**继续执行**（图片可能为外部 URL 或嵌入式 base64）
- 若无图片：跳过 Phase 2

### Phase 2: 图片识别（如有图片）

**目标：** 使用 Vision 能力详细识别 UI 截图/原型图

**强制模板：** 严格按照 `references/image-analysis-template.md` 中的模板输出，确保识别结果详细且结构化。

**模板选择规则：**
- 若图片包含票据操作表单（金额/日期/当事人字段/审批流程）→ 使用"票据操作页面识别模板"
- 若图片包含列表/表格/查询条件/分页 → 使用"票据列表页面识别模板"
- 其他情况（纯文本截图、流程图、架构图等）→ 使用"通用页面识别模板"

**识别要点（票据系统特有）：**
- 票据类型选择器（银承/商承/银转/商转等）
- 金额输入区域（大写/小写联动）
- 日期选择器（出票日/到期日/贴现日等）
- 状态标签（票据状态机各节点）
- 操作按钮（签收/拒绝/撤回等，需关注权限控制）

**Phase 2 完成门控：**
- 确认所有图片都有识别结果
- 若有遗漏：**⚠️ 发出警告提示**，但**继续执行**，用户可在后续迭代中补充

### Phase 3: 需求提取

**目标：** 保持用户原文一字不改，按功能模块组织内容

**核心原则：**
- 用户原文**一字不改**，完整保留
- AI 补充的内容用 `【补充】` 标记，明确贡献边界
- 按票据业务模块组织：出票、承兑、背书、贴现、质押、保证、交易、清算、兑付、追索等

**原文表格自动修复（例外规则）：**
用户原文中的 Markdown 表格若缺少 `|---|---|` 分隔行，**必须自动补充分隔行**，这不视为修改原文。这是为保证输出文档可被 Markdown 渲染器正确解析。

**补充边界：** Phase 3 仅补充与用户原文**直接相关**的明显延伸规则（如用户提到承兑，补充承兑的基本状态流转）。系统性规则审查由 Phase 4 的规则库驱动完成，Phase 3 不做全面扫描。

**输出结构：**
```markdown
## N. [功能模块名称]

[用户原文，保持原样]

---

**【补充】业务规则：**
- ...

**【补充】数据定义：**
- ...

**【补充】异常情况：**
- ...
```

### Phase 4: 三角色审查

**角色一：票据业务专家**

关注"功能对不对"——业务逻辑完整性

**审查执行步骤：**
1. 从 Phase 1 第5步的需求分类结果中，提取涉及的业务模块（如"承兑"、"额度管理"）
2. 从 `references/bill-business-rules.md` 中筛选与该模块相关的规则
   - 关键字匹配：规则描述中包含模块关键词（如"承兑"匹配承兑相关规则）
   - 通用规则必检：CRUD完整性、数据一致性、票据类型约束
3. 逐条检查需求文档中是否有对应描述
4. 对缺失的规则生成待确认问题

审查维度（详见 `references/bill-business-rules.md`）：
- CRUD 完整性：每个票据实体是否有完整的增删改查
- 状态流转闭环：票据状态机是否覆盖所有合法路径
- 金额校验规则：票面金额、交易金额、利息计算等
- 日期规则：出票日 ≤ 到期日、贴现日范围等
- 数据一致性：主表与明细表、票据与交易记录
- 票据类型约束：银承/商承/银转/商转各有不同规则

**角色二：票交所合规审查员**

关注"合不合规"——监管与规范符合性

**审查执行步骤：**
1. 从 Phase 1 第5步的需求分类结果中，提取涉及的业务模块
2. 从 `references/compliance-rules.md` 中筛选与该模块相关的规则
   - 报文规范必检：所有涉及票交所交互的功能
   - 风控规则必检：涉及额度、黑名单、反洗钱的功能
   - 通用规则必检：ECDS状态同步、异常票据库校验
3. 逐条检查需求文档中是否有对应描述
4. 对缺失的规则生成待确认问题

审查维度（详见 `references/compliance-rules.md`）：
- 票交所报文规范：报文字段完整性、必填项校验
- ECDS 状态同步：票据状态与电子商业汇票系统一致性
- 异常票据库校验：是否对接票交所异常/止付票据库
- 交易时间窗口：是否遵守票交所交易时段限制
- 风控规则：黑名单校验、额度管控、反洗钱规则
- 信息披露：商承信息披露要求是否符合

**角色三：体验审查员**

关注"好不好用"——交互体验与操作流畅度

**审查执行步骤：**
1. 从 Phase 1 第5步的需求分类结果中，提取涉及的业务模块
2. 从 `references/ux-rules.md` 中筛选与该模块相关的规则
   - 二次确认必检：涉及签收、拒绝、转让、质押等不可逆操作
   - 输入校验必检：涉及金额、日期、票据号码输入的页面
   - 通用规则必检：空状态处理、权限可见性
3. 逐条检查需求文档中是否有对应描述
4. 对缺失的规则生成待确认问题

审查维度（详见 `references/ux-rules.md`）：
- 二次确认：承兑签收、拒绝、贴现提交等关键操作的确认弹窗
- 输入校验：金额格式、日期范围、票据号码30位校验
- 空状态处理：列表无数据、查询无结果、下拉选项为空
- 权限可见性：无权限操作按钮的显示/置灰控制
- 票据特有交互：影像查看、状态标签颜色、批量操作反馈

### Phase 5: 生成输出

**输出前表格格式校验门控（强制执行）：**
在生成最终文档前，必须对所有 Markdown 表格执行以下校验，**任一表格不通过则必须修复后再输出**：

1. **分隔行检查**：每个表格第二行必须是 `|---|---|` 格式的分隔行
2. **列数对齐检查**：表头行、分隔行、每一数据行的列数（`|` 数量 - 1）必须完全一致
3. **分隔符格式检查**：分隔行每列必须包含至少 3 个 `-` 字符（如 `|---|`）
4. **修复动作**：若发现不合规表格，自动补充分隔行或对齐列数，不视为修改原文

校验通过后方可进入文件输出步骤。

**OriginalStem 变量定义：**

输出文件名中的 `[OriginalStem]` 按以下规则提取：
- 若源文件为完整路径（如 `河南农商个性化需求/额度.md`），取文件名去掉扩展名部分 → `额度`
- 若为多个文件合并，取第一个文件的主干名
- 若为直接粘贴文本，使用 `需求文档` 作为默认值
- 若需求中明确提到项目名称（如"承兑行额度管理"），使用该名称

**输出文件：**

| 文件 | 命名规则 | 说明 |
|------|----------|------|
| 主文档 | `[OriginalStem]-v1.md` | 完整 PRD 文档，含原文 + 【补充】内容 |
| 待确认清单 | `[OriginalStem]-待确认-v1.md` | 需用户确认的问题清单 |

**输出路径：** 与需求源文件同级目录。若源文件在 `河南农商个性化需求/` 下，输出到该目录；若直接粘贴文本，输出到 `bemp-generate-prd/output/`。

**主文档结构（详见 `references/document-templates.md`）：**
1. 文档信息（版本、作者、日期）
2. 需求概述
3. 业务背景与目标
4. 功能需求详情（按模块组织）
5. 票据业务规则（状态机、金额、日期等）
6. 数据定义（字段、校验规则）
7. 接口需求（票交所接口、内部接口）
8. 非功能需求（性能、安全、合规）
9. 异常处理
10. 待确认问题汇总

**待确认清单结构：**
```markdown
# 待确认问题清单

## 🔴 阻塞项（必须确认才能继续）
1. [问题描述]
   - 背景：...
   - 选项A：...
   - 选项B：...

## 🟡 建议项（建议确认以提升质量）
1. [问题描述]

## 🟢 提示项（已做默认假设，可后续调整）
1. [问题描述] → 默认假设：...
```

## 迭代完善机制

### 版本号规则

| 版本 | 含义 |
|------|------|
| `v1` | 初版，含待确认清单 |
| `v2` | 用户确认后，已确认的【补充】内容移入正文 |
| `v3+` | 继续迭代 |

### 迭代操作

用户查看待确认清单后，直接回复确认：

```
问题1需要补充，票据类型包括银承和商承两种，不支持银转。
问题2不需要，产品已明确只做线上贴现。
问题3待讨论，下周和票交所确认后再定。
```

AI 自动解析并生成新版本：
- **文件操作**：在原输出目录生成新文件（如 `[OriginalStem]-v2.md`），**不覆盖**旧版本文件
- 已确认的补充内容：移入正文，移除【补充】标记
- 不需要的补充内容：删除
- 待讨论的：保留在待确认清单，标记为"待定"

### 迭代门控

每次迭代前检查：
1. 上一版本的所有阻塞项是否已处理
2. 新增内容是否引入新的待确认问题
3. 文档结构是否完整

## 与 BEMP 工作流集成

本技能在 BEMP 标准化闭环流程中的位置：

```
需求梳理 ──→ 方案设计 ──→ 代码同步 ──→ 代码开发 ──→ ...
    │
    ├── bill-requirement-analyst (智能体：需求分析/梳理)
    └── bemp-generate-prd (本技能：需求文档生成/补全)
```

**协作关系：**
- `bill-requirement-analyst`：负责需求分析与梳理，输出需求要点
- `bemp-generate-prd`：负责将需求要点转为结构化 PRD 文档
- `bemp-advanced-doc-generator`：负责从 PRD 生成详细设计、测试用例等交付文档

**典型流程：**
1. 用 `bill-requirement-analyst` 梳理需求要点
2. 用 `bemp-generate-prd` 生成完整 PRD
3. 团队评审确认 PRD
4. 用 `bemp-advanced-doc-generator` 生成详细设计和测试用例

## 智能体操作指南：测试假设自动推演

当 Phase 4 三角色审查产出阻塞项时，自动执行以下推演步骤，将不确定项转化为可执行的测试假设：

### 执行步骤

1. **读取配置**：加载 `config/prd-assumptions-config.json`
2. **匹配模板**：对每个阻塞项，用关键词匹配 `assumption_templates` 中最相关的条目
3. **生成测试假设**：按 `assumption_application_rules` 中对应级别的输出格式生成
   - 阻塞项(🔴)：`Q-{序号}：{问题描述} → 测试假设：{default_assumption}（{reason}）`
   - 建议项(🟡)：附推荐假设但不强制
   - 提示项(🟢)：直接应用默认假设
4. **写入待确认清单**：将测试假设写入待确认清单，标注"测试假设"来源

### 匹配规则

- 逐条扫描阻塞项描述，提取关键词
- 与 `assumption_templates[].keywords` 做交集匹配，取匹配数最多的条目
- 若无匹配，使用"接口/配置取值不确定"作为默认模板
- 匹配结果列在待确认清单的"推荐假设"列

### 配置文件

| 文件 | 说明 |
|------|------|
| `config/prd-assumptions-config.json` | 假设模板库 + 应用规则 |

> 新增假设类型时，只需在 `assumption_templates` 数组中追加条目，无需修改技能逻辑。

## 核心设计原则

1. **人机协作**：AI 负责发现遗漏和补全规则，人类负责业务决策确认
2. **原始内容保护**：用户原文一字不改，AI 补充用【补充】标记
3. **渐进明细**：从粗到细，多轮迭代，避免一次性追求完美
4. **专业分工**：票据业务专家关注业务逻辑，合规审查员关注监管合规，体验审查员关注交互流畅度
5. **票交所合规优先**：所有补充内容必须符合上海票据交易所规则与接口标准
6. **可追溯**：保留原始内容、标记 AI 补充、记录迭代历史

## 适用与不适用

**适合用：**
- 需求来源是会议纪要、草稿、口头描述，缺少票据业务细节
- 有 UI 设计稿需要转成文字需求，补全票据操作交互逻辑
- 业务给的功能清单太简略，需要补全票据状态流转、金额校验规则
- 需要确保需求文档覆盖票交所合规要求

**不适合用：**
- 需求已经非常明确详细（直接进入开发更快）
- 需要全新票据产品设计（AI 只能补漏，不能创新业务模式）
- 纯技术架构设计（非需求层面）

## 注意事项

1. **图片识别需要带视觉能力的大模型**，实测 Kimi 2.5 效果不错
2. **票据业务规则复杂**，生成后务必请业务人员确认
3. **合规要求随政策变化**，审查结果需与最新票交所公告核对
4. **银行个性化差异大**，不同银行的票据业务规则可能不同，需明确目标银行
