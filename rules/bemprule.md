# 通用强制准则
- 所有开发任务优先遵循代码复用原则
- 不同业务动作固定绑定指定智能体 / 技能，不可随意调用
# 任务 - 智能体绑定清单
- /spec、/plan 指令：调用bemp-personalized-dev技能
- 项目开发/方案设计/代码编写/BUG 修复/代码走查：bemp-personalized-developer
- 常规测试/用例编制/功能测试：bemp-auto-tester
- 二轮调试测试：chrome-devtools-debugger
- 用例评审：test-lead-reviewer
- 开发/测试 前 需求分析/需求梳理：bill-requirement-analyst
- 开发/测试 前 启动服务/代码同步/代码扫描：bemp-implementation-engineer
- 输出交付文档：document-delivery-engineer
# 标准化闭环流程
## 完整开发流程
- 需求梳理→需求确认→方案设计→代码同步→代码开发→代码评审修复→代码质量扫描→启动服务(并行)→测试用例编制→用例评审(门禁)→功能测试→二轮调试测试→缺陷修复验证→输出交付文档
## 快速测试流程
- 需求梳理→需求确认→测试用例编制(并行启动服务)→用例评审(门禁)→功能测试→二轮调试测试→缺陷修复验证→输出交付文档
# 流程门禁规则
## 需求确认门禁
- 需求梳理完成后，必须对"待确认事项"进行闭环处理
- 已闭环项：正常进入下一环节
- 未闭环项（可假设）：标记为"测试假设"，在用例中明确标注假设前提
- 未闭环项（不可假设）：标记为"阻塞项"，影响核心流程时必须等待确认
## 用例评审门禁
- 通过：严重问题数=0 且 主要问题数=0 → 允许进入功能测试
- 有条件通过：严重问题数=0 且 主要问题数>0 → 允许进入，主要问题需在执行前修复
- 有条件通过（需回退）：严重问题数>0 → 回退至用例编制修复，修复后重新评审
- 不通过：用例整体质量不达标 → 回退全面重写
## 缺陷闭环门禁
- P0/P1 缺陷必须修复并验证通过后，方可进入交付文档阶段
- P2/P3 缺陷可记录为"已知问题"进入交付阶段，但需在交付文档中明确列出
# 并行启动规则
- 服务启动与需求梳理/用例编制/用例评审无依赖关系，应并行执行
- 前端启动与后端启动无依赖关系，应并行执行
- SpringBoot 依赖 Redis 和 ZooKeeper 就绪，Frontend 与后端无启动依赖
# 服务启动规则
- 启动任何服务前必须先检测该服务是否已在运行，已运行且未要求重启则跳过
- 用户要求"重启"或"重新启动"时，等价于强制重启，自动停止旧进程后重新启动
# 最终要求
- 项目严格依照上述流程顺序执行，全流程闭环落地，确保项目达到正式交付标准。
- 每个门禁环节必须严格执行，不得跳过或降级。
